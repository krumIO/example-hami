# Deploy HAMi from Rancher Apps

The same install as [`../deploy-with-helm/`](../deploy-with-helm), driven through Rancher instead of the CLI. Rancher's Apps system is Helm underneath, so the values are identical — read that scenario first for what they mean and why two of them are load-bearing.

Worth knowing before you start: the Rancher UI form for a third-party chart is just a YAML editor over the chart's values. There's no HAMi-specific form, so you're typing the same YAML either way. The advantages here are that the chart repo becomes visible to everyone with cluster access, and upgrades show up as available versions rather than something you have to notice.

## 1. Add the chart repository

**UI:** ☰ → your cluster → *Apps* → *Repositories* → *Create*. Name it `hami`, choose *http(s) URL to an index generated by Helm*, and enter:

```text
https://project-hami.github.io/HAMi/
```

**Declaratively**, which is preferable if you manage more than one cluster — a `ClusterRepo` is what the UI creates anyway:

```sh
kubectl apply -f clusterrepo.yaml
```

See [`clusterrepo.yaml`](clusterrepo.yaml). Rancher reconciles it into the same repository entry, so the chart appears in the UI for anyone who prefers clicking.

## 2. Install the chart

*Apps* → *Charts*, set the filter to the `hami` repository, choose **HAMi**, and pick version **2.9.0**.

On the *Values* step, switch to **Edit YAML** and paste the contents of [`../deploy-with-helm/values.yaml`](../deploy-with-helm/values.yaml). Do not rely on the rendered form for `nvidiaNodeSelector`: the form merges into chart defaults exactly as Helm does, so a selector added there sits *alongside* the default `gpu: "on"` rather than replacing it, and the DaemonSet quietly ends up requiring both labels. The `gpu: null` line is what removes it, and expressing that is much clearer in YAML.

Install into the **`kube-system`** namespace.

## 3. Label the GPU nodes

Nothing schedules until nodes match the selector. In the UI: *Nodes* → select node → *Edit Config* → *Labels* → add `gpu-plugin=hami`. Or:

```sh
kubectl label node <node> gpu-plugin=hami --overwrite
```

## 4. Verify

Rancher will show the app as *Deployed* as soon as Helm succeeds, which happens well before the device plugin is actually working — a crash-looping DaemonSet does not make the app red. Check the real signals:

*Workloads* → *DaemonSets* → `hami-device-plugin` should be Running on each labelled node, not restarting. Then, from the cluster's kubectl shell (☰ → *Kubectl Shell*):

```sh
kubectl get node <node> -o jsonpath='{.metadata.annotations.hami\.io/node-nvidia-register}{"\n"}'
kubectl get node <node> -o jsonpath='{.status.allocatable.nvidia\.com/gpu}{"\n"}'
```

Then run the smoke test from [`../../samples/`](../../samples) to confirm the memory limit is enforced inside a container.

## Upgrading

*Apps* → *Installed Apps* → HAMi → *Upgrade*. Rancher preserves your values across the upgrade; re-check the rendered `nodeSelector` afterwards if the chart's defaults changed between versions.

## When not to use this path

If GPUs are already in use on the cluster via `nvidia-device-plugin`, installing from the UI has the same hazard as installing from the CLI, with less visibility: the admission webhook starts redirecting every GPU pod cluster-wide the moment the app reports *Deployed*. Use [`../migrate-nvidia-to-hami/`](../migrate-nvidia-to-hami), which sequences the webhook deliberately.

For fleets of clusters, [`../deploy-with-fleet/`](../deploy-with-fleet) is the better fit — a `ClusterRepo` plus a per-cluster app install is more clicking than a single bundle targeting a label.
